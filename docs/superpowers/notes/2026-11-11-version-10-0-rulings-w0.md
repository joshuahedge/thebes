# Version 10.0, Track 0: rulings 2100-2109 (the seams)

Where the plan's code and the real code disagreed, the code won; each ruling says both.

- **2100. `zoomAt` holds by the view now; `panBy` only once it is given one.** As the plan writes: `zoomAt` ends with `holdInMap(cam, view)`, and `panBy(cam, dx, dy, view = null)` holds with a zero margin (the 6.0 clamp) when no view is passed, which no caller does yet. So until Track F passes the view to the pans (`src/ui/input.js`, `src/ui/keyboard.js`, `src/ui/cameraControl.js`'s fling), a zoom near the map's edge pulls the centre in by the margin and the next drag can take it back to the edge. The full suite passed with it (the 6.0 edge tests pan without a view). Cost if wrong: none shipped; Track F makes the two agree.
- **2101. Life's ids are 2000000-2799999, not 1600000-1999999; `walkSlotFor` takes the renderer's object.** The plan's ranges fall inside wildlife's span (`WILDLIFE_ID_BASE` 1400000 + a number below 600000): its lodge and wharf figures are 1700000 + 3 x building id, so a lodge with id 0 would have shared ids with river life, and building ids from 33334 with builders. `LIFE_IDS` is `{ townsfolk: 2000000, river: 2200000, builders: 2400000, crowd: 2600000 }`, the free band between wildlife and the carts (3000000), 200000 a range; the id comment in `src/render/wildlife.js` lists it, and the test checks the band. The plan's `walkSlotFor(kind, 0, 0)` is `walkSlotFor({ slot, x, y, dir, stand }, registry)` in the code; the test calls that. The placeholders: `child` is a citizen at 0.75, `builder` a citizen with a mud band at the waist, `goat`, `dog` and `crocodile` flat ovals in the lavender shade (`WASH[2]`) on a `footShadow`, each its own size, because `tests/render/figuresArt.test.js` walks `FIGURE_KINDS` through `fig()` and wants every kind's pixels distinct and inked (so the placeholders are drawn inside `fig()`, not only in `FIGURE_ART`). A render-only crocodile already exists as `fig.croc` (wildlife, `TILE_SLOT.croc`); Track L may draw `fig.crocodile` by it or retire one. Cost if wrong: renumbering is one table; the spec's 5a-5d text names the old numbers.
- **2102. The life seam keeps the v90 dropper as it is, so the dropping test runs 200 frames.** `createDropper({ budgetMs, order })` has `account(ms, now)` and `off(kind)`, not `spend`/`dropped`; `createLife` adds those: `spend(name, ms)` adds to the frame's total, and a frame is every call with the same `now()` (createUI passes `() => frameNow`, the render's frame time), accounted once when `now()` moves on, so several hooks a frame make one figure. Each hook a source has (`walkers`, `ground`, `late`) is timed into the budget under its name; a dropped source's hooks are skipped; under Still (the level or the frame's motion) nothing runs. The dropper holds a level `V90_HOLD_MS` (2 s) and counts the hold from its first frame, so 120 frames of 16 ms (1.9 s, the plan's test) cannot drop; the test runs 200 (3.2 s) and restores over 1200 frames as written. `addSource` takes `{ name, walkers?, ground?, late? }` (what the plan's test passes; `addSource(name, hooks)` works too) and refuses a name outside `LIFE.dropOrder`. The wiring in `src/ui/createUI.js`: walkers after `v70Walkers`, `life.ground` after `ambient.draw`, `life.late` in the `fire` closure right after `drawFires` (which ends with the late ambient, `drawAmbientLate`) and before `drawIllness`; `ui.life` is exposed for tests and Track L. `deviceKind` defaults to `spriteCache.js`'s `DEVICE_KIND` (a constant, not a function). Cost if wrong: a 1-second hold for life alone would be one option to `createDropper`.
