# Version 9.1 "First hours": rulings 1685-1699 (Track P, runs well)

The profile tools/profile.ps1 (with its server tools/profile-serve.py); the caches by bytes in src/render/terrainBaker.js (`TERRAIN_BUDGET_BYTES`, `CACHES_BUDGET_BYTES`, `chunkBytes`, `frame`, `trim`, `bytes`, `room`) and src/render/spriteCache.js (`SPRITE_IDLE_MS`, `SPRITE_BUDGET_BYTES`, `frame`, `bytes`, `buckets`, `drops`), wired in src/render/renderer.js (the baker told the chunks shown and the frame's budget, the sprite cache told a frame began, the ring's pre-bake asking `room`, the walk warm-up after a dropped bucket, `cacheBytes`); index.html's module preload block written by tools/sw-files.ps1. Tests: tests/v91/p/ (and tests/v91/w0/seams.test.js's checks of the empty blocks and of `caches()` updated for what P filled).

1685. No bundler: the module preload block is generated by `tools/sw-files.ps1` (every module src/main.js imports through static import and export-from lines, depth first, main.js first; a dynamic `import()` stays lazy) and kept only if P1 improves. — Cost if wrong: a slow first load stays slow until a bundle is chosen.
1686. The caches budget by bytes: terrain chunks by a canvas byte budget (48 MB, fixed whatever the ratio: at DPR 1 it holds about 21 chunks at zoom 1, still under the count of 32), sprite buckets dropped when unused, never in view. — Cost if wrong: more re-bakes when a player zooms back and forth.
1687. A chunk the frame shows is never evicted for the budget, at any scale, and the terrain gives way to the sprites: each frame its budget is the lesser of 48 MB and 64 MB less the sprites held, never under 16 MB (so a sprite-heavy view keeps its ring rather than letting it go and baking it again), set as the frame begins and again after the sprites are drawn, so the two keep target P3's 64 MB together; a view that itself needs more (a hilly view at zoom 2 at DPR 2, where every hill is its own sprite slot, about 0.8 MB each) holds only what it shows. The ring's pre-bake bakes ahead only into room the budget has once chunks the frame has not looked at are let go. — Cost if wrong: zooming back to a part of the map left a while ago re-bakes a few chunks; the worst hilly view holds about 77 MB.
1688. The profile (tools/profile.ps1) is headless Edge at 390x844, DPR 2, through tools/profile-serve.py (gzip as the real host, HTTP/1.0, no-store, so a warm load can only use the service worker); the ready point is the page's `thebes-ready` mark when set, otherwise the title card appearing (the table says which); a frame's cost is the drawn frame's whole requestAnimationFrame callback (the days ticked and the draw), and memory is the JS heap after a forced collection, `window.__thebes.caches()` and a census of every live canvas. Headless Edge draws canvas without a GPU and the machine runs other suites, so the frame figures bound the obvious, not a phone. — Cost if wrong: a figure off by the machine's load; Josh's real-phone pass is the check.
1689. The sprite cache drops a zoom bucket left for 30 s whole, never the bucket in use, and keeps 16 MB by the sprites least recently drawn, never one this frame draws (a cache used without frames evicts nothing). The renderer warms a figure's walk poses again after a bucket is dropped, not after a single sprite is evicted (that pose is drawn again when next needed, so the budget never makes the warm-up loop). — Cost if wrong: a figure's turn at a long-unused zoom draws its pose then, a millisecond or two.
1690. The profile's session is compressed: the seed-11 sample town on a Large map, its days ticked by the sim's own `tickDay` with the events handed to the interface as the loop does, a frame drawn by the interface's own `render` every 10 days, and the camera over every chunk at every zoom bucket after each 10 minutes of play (three game years), not each game year, so 2 hours of play fit the profile's 10 minutes on this machine. — Cost if wrong: the session pans less often than a restless player; the suite's P3 test pans the whole map at every bucket.
1691. Frames (P2, P4) are measured and reported, with the biggest costs from the profile's CPU sampling (`-Layers`); no frame code is changed in this release (design 5d). — Cost if wrong: a slow phone stays slow until a frame track takes the biggest cost.
1692. The module preload stays (ruling 1685's test): the throttled cold load's ready point was 17.2 and 17.5 s with it against 17.8 and 18.0 s without it on the same tree (and 18.1 to 18.8 s on 9.0), about 3% better. The profile's server speaks HTTP/1.0, so the browser fetches six at a time and the preload can only fill the gaps; on the real host's HTTP/2 every preloaded module is asked at once. — Cost if wrong: 377 link lines in index.html (about 2 KB gzipped) for half a second.
1693. The warm load (P1's 1.5 s) is not measured: in headless Edge here the service worker's install ends redundant, though the same page caching the same list with `addAll` succeeds; it goes on Josh's real-phone list (install, then launch offline) with the question whether the offline cache installs at all. — Cost if wrong: a warm load or offline start that does not work is found on a phone, not here.
